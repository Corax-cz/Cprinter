> 状态：待你确认后开工。本文档基于对 brlaser 源码、google/virtual-printer 源码、以及本机环境的**实际核查**，不是纸面推演。

## 1. 结论

**可行。四层切割（IPP → PDF 光栅化 → Native 编码 → USB Bulk）是正确的，不需要 Root、不需要 CUPS。**

但在动手前必须修正规格书里 **5 处与实际代码不符** 的地方，否则 Stage 1 会按错误假设走弯路：

| # | 规格书说法 | 实际代码 | 影响 |
|---|---|---|---|
| 1 | JNI 传「灰度像素，每像素 1 字节」 | `brlaser/src/main.cc:177` 硬校验 `cupsBitsPerPixel == 1`，**只吃 1bpp 位图** | 半色调（灰度→1bpp）必须我们自己实现，brlaser 上游是 CUPS 干的 |
| 2 | 双面指令 `ESC&l#S` 参数「需查手册或实验确定」 | `brlaser/src/job.cc:81-83` 明写 `ESC&l2S` | 不用猜，已有正确答案 |
| 3 | 「剥离 cupsRasterReadPixels」 | 真正要改的只有 `main.cc:48-53` 的 `next_line()`（6 行）。`job.cc` / `line.cc` / `block.h` 一行都不用动 | 剥离成本比预期低一个数量级；字节一致性天然成立 |
| 4 | 保留 `services/printer/`、`services/discovery/` | 仓库是**单模块** `app/`，不是多模块；接缝在 `processor/DocumentProcessor.kt` | 改造成本低；但目录结构要按实际重建 |
| 5 | 忽略许可证 | brlaser 是 **GPL-2.0-or-later**，virtual-printer 是 Apache-2.0 | APK 整体必须取 **GPL-3.0**（GPLv3 与 Apache-2.0 兼容，GPLv2 不兼容）。自用无碍，README 要写明 |

## 2. 事实核查结果（附证据）

### 2.1 打印机与 brlaser 的匹配度：高

- 联想 LJ2600D 用的是 **Brother HL-2240D 机芯**，官方驱动即 Brother `BrGenML1`（GDI/主机型打印机，不是通用 PCL）。
- `brlaser/README.md` 已列：`HL-2220 series`、`HL-2270DW series`、`Lenovo M7605D`。你的机型落在覆盖范围内。
- 你现有 Termux + CUPS 跑的就是 brlaser → **手机上已经有一条能出纸的参考链路**，Stage 1 的「黄金参考」不必另搭，可直接取用。

### 2.2 brlaser 的输出到底是什么（已读源码确认）

`job.cc` 的完整输出结构：

```
[128 × 0x00]
\033%-12345X@PJL\n  @PJL JOB NAME="..."
每页:
  \033%-12345X@PJL\n
  @PJL SET RAS1200MODE / RESOLUTION / ECONOMODE / SOURCETRAY / MEDIATYPE / PAPER / PAGEPROTECT / ORIENTATION
  @PJL ENTER LANGUAGE = PCL\n
  \033E                        ← PCL 复位
  \033&l<n>X                   ← 份数
  \033&l2S                     ← 双面（仅 duplex 时）
  \033*b1030m                  ← Brother 私有压缩模式 1030
  [每 64 行一个 band 的压缩数据]
  1030M\f                      ← 结束 + 换页
结尾:
  \033%-12345X@PJL\n  @PJL EOJ NAME="..."\n  \033%-12345X\n
```

即：**PJL 包裹 + PCL5 光栅 + Brother 私有 1030 压缩**。规格书称之为「PCL 字节流」大体没错，但真正的难点是 1030 压缩，而这块 `line.cc` / `block.h` 已经实现，我们只搬不改。

### 2.3 剥离的真实工作量

`main.cc` 只有 208 行，其中与 CUPS 耦合的只有：

- `cupsRasterOpen` / `cupsRasterReadHeader2` / `cupsRasterReadPixels`（3 个调用）
- `cups_page_header2_t` 结构体（`build_page_params()` 里取 7 个字段）

而 `job` 类是往 `FILE*` 里写的。Bionic 自 API 23 起提供 `open_memstream()`，因此：

```
JNI 入口 → 灰度缓冲 + 参数
        → 内部灰度转 1bpp（Bayer 8×8，可切换）
        → open_memstream(&buf,&len) 造一个内存 FILE*
        → job.encode_page(params, height, bytesPerLine, nextline_from_memory)
        → 关闭流，把 buf 拷成 jbyteArray 返回
```

`job.cc`/`line.cc`/`block.h` **原样编译**，这就是「字节级一致」的物理保证——同一份编码代码，只有像素来源不同。

### 2.4 一个白捡的验证工具

`brlaser/src/brdecode.cc` 是官方附带的**解码器**（把 1030 流解回位图）。它让我们在**没有打印机**的情况下完成部分 Stage 1 验收：编码 → 解码 → 与原测试图案逐像素比对。硬件不再是唯一的验收闸门。

### 2.5 IPP 层（google/virtual-printer，Apache-2.0，真实存在）

- 单模块 `app/`，包结构：`printer/PrinterService.kt`（Ktor + HP JIPP 0.7.16）、`processor/DocumentProcessor.kt`（**要替换的「存盘+展示」后端**）、`queue/PrintJobQueue.kt`、`printer/PrinterForegroundService.kt`。
- HTTP 用 **Ktor + Netty**；mDNS 用 **Android NsdManager**（不是独立 DNS-SD 库），服务类型 `_ipp._tcp.`，端口 8631。`minSdk 29 / compileSdk 35`，与我们的约束一致。
- 结论：**替换 `DocumentProcessor` 的内部实现即可**，协议层不动。这一步风险很低。

## 3. 规格书没写、但会真正卡住项目的风险

### R1　本机没有任何 Android 工具链（**当前唯一硬阻塞，已实测**）

`java` / `gradle` / `adb` / `cmake` / `ninja` 全部不存在，`ANDROID_HOME` 为空，`%LOCALAPPDATA%\Android\Sdk` 不存在，无 Android Studio。D 盘剩余 394 GB。
→ 必须先自举：JDK 17 + cmdline-tools + platform 35 + build-tools + NDK r26 + CMake（约 4 GB 下载）。

### R2　600 dpi 整页 Bitmap 会 OOM（**必须改设计**）

A4 @ 600 dpi = 4961 × 7016 = 3480 万像素：
- `ARGB_8888` 单页 **≈ 139 MB**（必崩）
- 即使 300 dpi 也要 **≈ 35 MB**（勉强）

→ Stage 2 **不能用整页 Bitmap**。改为**条带渲染**：`PdfRenderer.Page.render(bitmap, destClip, transform, RENDER_MODE_FOR_PRINT)`，每次渲 128 或 256 行高的一条，转 1bpp 后立即交付编码器。规格书给的 `Bitmap.createBitmap(page.width*scale, page.height*scale)` 写法在真机上会 OOM。

### R3　USB OTG 与充电互斥（部署层风险）

手机只有一个 USB-C 口。打印机接上后手机不充电，"家用打印服务器"长期跑就是持续掉电。要么上带供电的 USB HUB / OTG Y 线，要么接受"打印时才插"。**这是产品形态问题，不是代码问题，需要你拍板。**

### R4　前台服务 + MIUI 杀后台

不常驻 = 不可用。需要 `startForeground`（`FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE`）+ 引导用户关闭电池优化。MIUI 尤其激进。

### R5　AirPrint（iOS/macOS）不支持纯 PDF

只广播 `document-format-supported = application/pdf` 时：
- **Windows** 手动 IPP（`http://IP:8631/ipp/print`）可以正常添加、正常打印 ✅
- **macOS / iOS AirPrint** 多半拒绝添加，因为 AirPrint 要求 **URF 或 PWG-Raster**，不接受客户端发 PDF 由服务器渲染。

→ Stage 3 验收标准**只对 Windows + 手动 IPP 承诺**。AirPrint 作为 v2，工作量（PWG-Raster 编码器）大于本项目其它所有层之和。若你只需要 Windows 打印，本项目完全成立。

### R6　NsdManager 注册的可靠性

`NsdManager.registerService` 在不少机型上"报注册成功但对 macOS/iOS 不可见"，且无法完全控制 TXT 记录。退路：**JmDNS**（纯 Java）+ `MulticastLock`，可自行写 TXT（`pdl`、`URF`、`rp`、`ty`），这也是绕开部分 WiFi 驱动组播过滤的唯一可控手段。已预留切换点。

### R7　1bpp 半色调质量

brlaser 上游由 CUPS 的 `pdftoraster` 做 dithering，质量不归它管。我们自己实现：Bayer 8×8 在 600 dpi 下打文本足够；大面积灰阶会有可见纹理，必要时换误差扩散（Floyd–Steinberg）。**Stage 1 的测试图案是纯黑白，不涉及灰阶，所以字节对比不被此风险污染。**

### R8　双面反向

`ESC&l2S` 只告诉打印机"开启双面"，背面正立由打印机翻转单元完成，CUPS 侧不重排。但如果纸张尺寸选项与实际纸盒纸张不一致，背面会错位。Stage 1 双面验收必须固定 A4 + 纸盒实际装 A4。

## 4. 修正后的实施计划（严格串行）

### Stage -1　工具链自举（已完成）

**决定：全部由我安装在 `toolchain/` 下，不使用 Android Studio 图形界面。**
理由：构建只需 JDK + SDK + NDK + Gradle CLI；IDE 是编辑器，装了我也点不了它。
装的是 Android Studio 背后同一套工具链（JDK 17 / platform 35 / build-tools 35 / NDK 27 / CMake），
工程用 `./gradlew` 构建；你以后想用 IDE 打开这个工程，直接 Open 即可。

**验收**：`./gradlew :app:assembleDebug` 出 APK，`adb version` 可执行。

### Stage 0　USB 发现与端点确认（0.5 小时）

`UsbManager` 按 VID `0x17ef` / PID `0x5411` 枚举 → `requestPermission(PendingIntent)` → `openDevice` → 遍历 interface 找 `USB_ENDPOINT_XFER_BULK` + `USB_DIR_OUT` → Logcat 打印端点地址、`wMaxPacketSize`、接口号。
**验收**：Logcat 出现 `Bulk OUT endpoint found: 0xXX (maxPacket=64)`。
**失败即停**：拿不到端点说明路径 B 的 USB 前提不成立，立即报告，不进 Stage 1。
**附带**：同时读一次 `GET_PORT_STATUS`（class 请求 0x00/0x01），把"缺纸/盖开/忙"作为后续状态反馈的种子。

### Stage 1　Native 渲染核心（**硬里程碑**，1.5–2 天）

1. 建 NDK 工程：`brlaser` 的 `job.cc`/`line.cc`/`block.h`/`debug.cc` 原样进 `app/src/main/cpp/brlaser/`，`main.cc` 不进（它是 CUPS filter 的 main）。
2. 写 `bridge.cpp`：
   - JNI 签名按规格书**保持不变**（`pixels: ByteArray, width, height, bytesPerLine, dpi, duplex, paperSize -> ByteArray`）；
   - 内部：灰度 → 1bpp Bayer 8×8 → `open_memstream` → `job::encode_page`；
   - 另加一个**仅供测试**的 `nativeRender1bpp(packed: ByteArray, ...)`，用于和参考实现做无半色调干扰的字节对比。
3. PC 侧参考 harness（同目录 `tools/hostref/`，用 NDK 的 clang 编成 Windows exe）：同一份 `job.cc`，把 `next_line` 换成读 `pgm/pbm` 文件。**同一份编码代码 + 同一份输入 → 输出必须逐字节相同**。这是"黄金标准"在本机可执行的形式，不依赖桌面 Linux。
4. 交叉验证：`brdecode` 解回位图 → 与原图案逐像素 diff。
5. 上机：测试图案（200×200 白底 + 中心 60×60 黑块，600 dpi 下按比例放大到 A4 居中）→ `bulkTransfer` 分块（≤16384，-1 退避 3×500ms）→ 出纸。
6. 双面：同一图案 `duplex=true` 打两页，验证 `ESC&l2S` 生效、背面正立、不颠倒。

**验收（四条全过才算过）**
- ① 主机 harness 与 JNI 输出**字节完全一致**
- ② `brdecode` 解码结果与源图案**逐像素一致**
- ③ 打印机出纸，图案位置/尺寸正确
- ④ 双面模式方向正确
**失败即停**：用二进制 diff 定位第一个差异字节，报告卡点（字节流 / 不出纸 / 方向），不跳 Stage 2。

### Stage 2　PDF → 条带 → 编码（1 天）

`ParcelFileDescriptor` → `PdfRenderer` → **条带渲染（R2 修正）**：每带 256 行，`ARGB_8888` 局部 Bitmap → 必须 `eraseColor(WHITE)` → 灰度 → 1bpp → 追加编码 → 每页一次 `bulkTransfer` 流式写出（不整页驻留内存）。
**验收**：单页 PDF 出纸，内容与 PDF 一致；峰值内存 < 80 MB（`dumpsys meminfo` 实测）。
**已知限制**：加密 PDF、含透明蒙版的 PDF 不在范围（记录）。

### Stage 3　IPP + mDNS（1–2 天）

Fork virtual-printer → 保留 `PrinterService`（JIPP + IPP 2.0）与 NsdManager 广播 → **只重写 `DocumentProcessor`**：收到的 document 字节存 app cache → 校验 `%PDF` 魔数 → 交给 Stage 2 管线 → 回 IPP `successful-ok`，属性回填 `job-impressions-completed`。
清理依赖：移除 `pdfbox-android`、`tika`（被 `PdfRenderer` 替代，纯减重）。
**验收**：Windows「添加打印机」手动 IPP → 打印测试页 → 出纸。
**mDNS 失败不算失败**：记录现象即退回手动 IPP；若 NsdManager 不可见，切 JmDNS（R6）。

### Stage 4　队列、状态、错误（持续）

前台服务常驻、任务队列串行、`GET_PORT_STATUS` 轮询、缺纸/离线提示、`bulkTransfer` 重试策略收敛、多页循环、Compose 状态页（最简）。

## 7. 一句诚实的替代方案提示

如果目的只是"去掉 root 依赖"，Termux + `termux-usb` + CUPS 已经能在无 root 下完成同样的事，且你现成的配置几乎不用改。
路径 B 的真正价值在别处：**自包含 APK、无 Termux 环境维护、可开机自启、可做状态反馈 UI**。如果这些不是刚需，这 4 层管线属于过度工程。这句话不是劝退，是让你在投入之前知道自己在为什么付账。
