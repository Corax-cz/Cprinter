## 二、按版本

### v0.7.9 —— 给打印机改名

**要求**：能改打印机名字（客户端列表里显示的那一行）。

**为什么这个功能不是「加个输入框」**：名字同时是两处事实来源 —— mDNS 服务实例名
（`<名字>._ipp._tcp.local`，iOS / Windows / Android 的打印机列表读它）和 IPP 的
`printer-name` / `printer-info`。两者必须同源：只改一处，iOS 列表里叫「客厅打印机」、
点进去的打印面板显示 `Cprinter`，用户会以为自己加错机器了。所以
`AppSettings.effectivePrinterName()` 是唯一来源，`IppServer` 和 `PrintService` 都从它取。

**最容易漏的一步：mDNS 必须注销重注册**。服务名是**注册那一刻**写进 PTR/SRV 记录的，
改一个配置字符串对已经在跑的多播没有任何影响。`PrintService` 里为此多了一个
`liveInstance` 字段记「实际发出去的名字」，`applyProtocolsSync` 发现它与配置不一致时，
先停掉两套广播、`Thread.sleep(400)`、再走正常的注册分支。那 400ms 不是随手加的：
`NsdManager.unregisterService` 是异步回调，紧接着注册会撞 `FAILURE_ALREADY_ACTIVE`，
主服务就掉到自写 responder 上重发，客户端可能同时看到新旧两条记录。

**输入校验只做三件事，但每件都有理由**：

- **63 字节**（不是 63 字符）。DNS 标签硬上限，一个汉字 3 字节 —— 纯中文最多 21 字。
  超了 `NsdManager` 只回 `FAILURE_INTERNAL_ERROR`，不说原因，表现是「改名之后一个
  客户端都搜不到」。对话框实时显示 `n / 63` 字节数并禁用保存；`effectivePrinterName()`
  里另有一次按 UTF-8 边界的安全截断（防手改 prefs），不能直接切字节 —— 切在汉字中间
  会解出 U+FFFD，列表里就是一串「�」。
- **点号换短横线**。实例名会拼成 `<名字>._ipp._tcp.local`，名字里带点会被当成分隔符：
  系统 mdnsd 转义成 `\.`，而 iOS 走的是我们自己发的报文，两边写法不一致 → 同一台
  机器两个名字，或者解析不到。顺带把 `\`、`/` 也换掉。
- **空串 = 用默认名**，而不是把 `Cprinter` 存进配置。这样「恢复默认」之后再改默认名，
  这些人能跟着一起变，而不是把曾经的名字永久钉在配置里。

**做了什么**：

- `AppSettings`：新增 `printerName` + `effectivePrinterName()` / `normalizePrinterName()` /
  `truncateUtf8()`；新增 `K_NAME`。
- `PrintService`：`liveInstance` 与重注册逻辑（见上）。
- `IppServer`：`printerDisplayName()` 改为读配置；`printer-info`、状态页 `<title>`/`<h1>`、
  iOS 提示行全部跟着变。
- `ui/RenameDialog.kt`（新）：输入框初始全选（改名 90% 是整体替换）、实时字节计数、
  超限报错、恢复默认、保存。
- `SettingsScreen`：新增「对外名称」分区（在「打印机型号」之前 —— 同属"这台机器是谁"）。
- `TestPdf`：纸上 logo 下方的署名也取这个名字；超过 logo 宽度时改成右对齐往左长，
  再长按 160pt 缩字号，别顶到标题。
- `ShareScreen` / `Wizard`：说明文字里的「Cprinter」改成当前名字。

**验收（实测数据）**：

| 场景 | 结果 |
|---|---|
| 默认名 | `printer-name = Cprinter` |
| 改成「客厅打印机」后重启 | mDNS 注册 `客厅打印机`，IPP `printer-name = 客厅打印机` |
| 改成「客厅 打印机」（带空格） | 注册成功，NsdManager 接受 UTF-8 + 空格 |
| 在线改名（点「恢复默认」，不重启） | 42.578 注销 `客厅打印机` → 43.773 注册 `Cprinter`，IPP 同步变 |
| 名字带点 + 超长（31 字） | 注册为 `客厅-超长的打印机名字用来测试六十三字节的`（61 字节），点号已换短横线 |

**顺带记一个调试陷阱**：`run-as ... sed -i` 改 prefs 之后，**已经活着的进程不会重读**
（SharedPreferences 全进程缓存），而且 `apply()` 发现内存值与待写值相同就**根本不落盘**
（`commitToMemory` 里 `existingValue.equals(v)` 直接 continue）。所以会出现
「文件明明写着新名字、UI 和广播却还是旧名字」。排查顺序：先 `pidof` 看进程是不是在我
改文件之前就起来了（ColorOS 会在 `am force-stop` 后立刻把 STICKY 的前台服务拉起来），
要验证读路径必须让进程在写文件**之后**诞生。

### v0.7.7 —— 把 logo 换成真矢量（附带一个很隐蔽的栅格化陷阱）

**要求**：测试页右上角放 logo；启动页也放一枚，但要小、不要放大（「都糊了」）；
App 图标保持原来的黑白配色不动。

**做法**：

- 源图 `tools/logo/logo-src.jpg`（1299x1211，带渐变）。`tools/mklogo.py` 走
  Marching Squares → RDP 抽稀 → Catmull-Rom 拟合，输出 13 个闭环、448 个控制点的
  pathData，回填比对 IoU 0.967。阈值取 190 而不是 128：Wi-Fi 弧线是往右上淡出的，
  阈值太严会把弧线尾巴切掉。
- 生成**两份同源资源**：`drawable/ic_logo.xml`（启动页用）、
  `values/logo_path.xml`（字符串版，打印用）。改图只改脚本，两份一起重出。
- 测试页：30pt（约 10.6mm），右边距与正文对齐（`PAGE_W - 46`），顶边 52pt。
- 启动页：`Theme.Cprinter` 加 `windowBackground`（Android 11-）+ `values-v31` 的
  `windowSplashScreenBackground` / `windowSplashScreenAnimatedIcon`（Android 12+），
  固定 84dp。不显式指定时系统会拿 launcher 图标铺满中间那块，又大又糊。
  深色模式靠 `values-night/colors.xml` 覆盖 `raven_ink` / `splash_bg`，不用第二份路径。

**踩到的坑：`VectorDrawable.draw()` 会把矢量栅格化成位图。**

第一版就是 `context.getDrawable(R.drawable.ic_logo).apply { setTint(BLACK) }.draw(canvas)`。
屏幕上看没问题（屏幕本来就小），但生成出来的测试页 PDF 里，30pt 的 logo 是：

```
9 0 obj <</Subtype /Image /Width 30 /Height 30 /BitsPerComponent 8 ...>>
...
30 0 0 -30 519 82 cm
/X9 Do
```

**一张 30x30 像素的图贴到 30pt 的位置** —— 等于亲手把矢量又变回糊的位图，
和用户抱怨的完全是同一个毛病，只是换了个地方发生。原因是 VectorDrawable 带
tint/colorFilter 时会走自己的 bitmap 缓存（按 bounds 大小建位图）。
换成 `PathParser.createPathFromPathData()` 拿到 `Path` 直接 `drawPath` 之后，
内容流变成 `1.25 0 0 1.25 519 52 cm` + 448 段 `c` + `f*`，全文再无 `/Image`。

**验收方式（不靠纸）**：`exec-out run-as ... cat cache/jobs/*.pdf` 把作业 PDF 拉回来，
解压页面内容流，看上面那两条特征。注意必须用 `exec-out`，`adb shell cat` 会把
二进制流弄坏（zlib 直接报 invalid distance too far back，很容易误判成「PDF 坏了」）。

**没做**：launcher 图标保持旧乌鸦没换 —— 用户明确要求「不要改」。
因此图标和测试页 logo 现在不是同一张图，这是刻意的。

### v0.7.6 —— 能搜到，但一个作业都发不出去

**现象**：列表里有了 `Cprinter`，但点打印没反应。本机测试页也不出纸，iOS AirPrint
同样没反应。界面显示「缺纸」，可打印机面板自检正常。用户明确要求：状态不准就别显示。

**根因一：端口状态位读反了一格。**

`GET_PORT_STATUS` 只有一套位定义（USB Printer Class 1.0 §6.3.2）：bit3 `nFault`
**低**有效、bit4 `Select` 高有效、bit5 `PaperEmpty` **高**有效。所以

- `0x18` = nFault 1 + Select 1 + PaperEmpty 0 → **完全就绪**
- `0x20` = PaperEmpty 1 → **缺纸**

代码却用 `(status and 0x08) != 0` 判缺纸 —— 那是 `nFault`，`0x18` 下恰好为 1，
于是**就绪态被判成缺纸**。`JobStore.runJob()` 在写第一个字节前就 ABORTED，
客户端看到的就是「点了没反应」。三条路径（iOS / 安卓系统 / 本机测试页）全部命中。

成因值得记：早先观察到「抽开纸盒回 `0x20`、关上回 `0x18`」，两个读数都对，但结论
记反成「缺纸 0x18 / 就绪 0x20」，于是反推出「这台机芯不符合标准位定义」，还专门
写了一个并列两套解释的诊断端点。**实测值只能验证规范，不能替代规范** —— 一旦用
两次现象反推位定义，记反一个对应关系就会长出整套错误理论。

**根因二：iOS 单独索要的 4 项属性缺一项。**

`com.apple.PrintKit.PrinterTool` 在打开打印面板时会**只问这 4 项**：
`printer-state-reasons`、`media-source-supported`、`printer-input-tray`、
`printer-mandatory-job-attributes`。前 3 项有，第 4 项从未实现，还留着一句
「故意不声明」的注释 —— 那条注释是错的：RFC 8011 §4.2.1.10 与
`printer-state-reasons` 同理，空集就写单值 `none`。缺这一项，PrintKit 判定
「状态不明」，面板关掉、一个作业都不提交。

**改动**

- `isPaperEmpty()` 改判 bit5；新增 `UsbPrinter.PortState` + `portState()`，
  **全工程只在这一处做位运算**，`PrinterProbe` 删掉自己那一遍，`IppServer` 的
  双轨解释收敛成一套。
- `printer-mandatory-job-attributes = none`。
- 界面文案匹配从英文位名改为中文（`缺纸/故障/离线`），否则旧匹配会静默失效。
- 测试页反白小样 96x16pt → 62x11pt；诊断图灰阶条从 8% 页高整页通栏 → 2% 半栏。

**验证**：`0x18 就绪` → USB 写入 113496 字节 / 84 ms；App 内测试页 212911 字节 /
150 ms（压缩率 4.9%，上墨很淡）；iOS 那 4 项查询齐全；`ippcheck.py` 全绿。

**教训**：同一个硬件事实只能有一处解码。三处各写一遍 `and 0x08` 时，界面显示的和
实际拦截作业用的是不同判据，改一处不改另一处就互相打架。

### v0.7.5 —— `1setOf` 多值属性写法错误（本项目最贵的一个 bug）

**现象**：iPhone、Windows、ipptool 全都正常，只有 Android 的系统打印列表里从头到尾
没有这台打印机。mDNS 广播完全合规（`dns-sd -B/-L` 都能看到 `Cprinter`），
BIPS 日志里也有 `onPrinterFound()`，但 `dumpsys print` 的 `cached_printers` 里
永远没有它。

**根因**：`Ipp.Writer.attr()` 给 `1setOf` 的**每个值都写了完整属性名**。正确规则是
只有第一个值带名字，第 2..n 个值 name-length 必须为 0（RFC 8010 §3.1.5）。
CUPS 的 ipp 解析库只认第一个值，于是 BIPS 的 native 层读到的是：

```
media-supported  found; number of values 1     ← 声明了 3 个
canPrintPDF: 0                                 ← 声明里有 application/pdf
duplex: 0                                      ← sides-supported 有 two-sided
```

`canPrintPDF=0` 意味着「这台机器打不出我能生成的任何格式」（BIPS 只产 PDF / PCLm /
PWG-Raster），于是它**静默地把整台打印机丢掉**，不报错、不提示。

**为什么 iOS 和 Windows 没事**：iOS 只产 URF，而第一个值恰好是 `image/urf`；
Windows 直通模式下第一个值是 `application/vnd.hp-pcl`。两者都恰好落在「第一个值」
里。Android 刚好需要第二个值，所以只有它被打死。

**为什么三个月没查出来**：`tools/ipptest/ippcheck.py` 里那条判据写的是
「顶层出现空属性名 = 1setOf 写错」。**自检工具和服务器犯了同一个错，两边自洽，
测试永远是绿的。** 这是本项目最重要的一课：检查器的判据必须来自真实客户端的
解析器行为，不能来自实现者自己的理解。

**修复**：`Ipp.Writer` 增加 `prevName` 状态，`attr()` 里「与上一个属性同名 → 写空名」，
`group()` 清空。一处修改覆盖 `keywordList` / `enumList` / 多次 `mime()` / `resolutionList` /
多值 `uri` / 多值 collection。同时把 `IppServer.kt` 里写反的注释删掉（就是它把后面
的人带偏的），`ippcheck.py` 增加 `check_repeated_full_name()` 作为硬性失败项。

**验证数据**（同一台手机，改前 → 改后）：

```
media-supported found; number of values 1  →  3
canPrintPDF: 0                            →  1
duplex: 0                                 →  1
dumpsys print 无 Cprinter                  →  local_id=urn:uuid:470bc3b0-...
```

RMX3888 与 Mi 9 SE 的系统「可用设备」列表里都能看到 `Cprinter / 192.168.123.6`。

### v0.7.4 —— 共享服务自愈

**根因**：`_ipp._tcp` 广播是 `PrintService` 进程的一部分，服务不在，局域网里就
**没有**那条记录。而覆盖安装 APK 一定会杀掉前台服务，此前没有任何恢复机制；
`AutoResumeShare` 又要求 `USB 已连接 + 已授权`，重装后授权被撤销，恢复路径一起断掉。

**改动**：`MainActivity.onResume` 补起服务（用户重装后会「打开 App 看一眼」，这是最便宜
的自愈点）；`BootReceiver` 接 `MY_PACKAGE_REPLACED`；`AutoResumeShare` 去掉 USB 前置条件，
只认用户的共享意图（`share_enabled`）。

**教训**：这是当时最像根因的假设，但它只是**次要原因**。真正的主因到 v0.7.5 才找到。
「服务没跑」能解释「列表里没有」，却解释不了「服务跑着也没有」——当时没有做这个反证。

### v0.7.3 —— 退后台 20 秒端口失联

App 切后台约 20 秒后，`8631` / `9101` 从局域网不可达，但进程没被冻结、`netpolicy`
无限制、socket 仍是 LISTEN。逐项排除 Doze、白名单、进程冻结、断网之后，定性为
**Wi-Fi 后台省电丢入站包**。

修法：`PrintService` 持有 `WIFI_MODE_FULL_HIGH_PERF` 的 `WifiLock` +
`PARTIAL_WAKE_LOCK`，`onDestroy` 释放。验证：后台 45s / 80s 后 `curl` 仍 200。

### v0.7.1 / v0.7.2 —— USB 拒收的定性

- **TXT 里的 UUID 不能带 `urn:uuid:` 前缀**。`NsdServiceInfo` 会自己补一次，双前缀
  导致与 IPP 的 `printer-uuid` 对不上，BIPS 打出 `UUID mismatch ... rejecting
  capabilities` 后整份能力作废。改成裸 UUID 后消失。
- **`bulkTransfer` 返回 -1 要分两种**：秒返回 = 主机端点 halted；卡满 5 秒 =
  设备 NAK 拒收。后者软件救不回来。
- **真正的拒收原因**：用户把纸盒拉开了。此时 EP0 的 `GET_PORT_STATUS` 仍然返回
  `0x20`（看起来就绪），但 bulk OUT 一个字节也不收。所以错误文案的排查顺序改成
  **先查纸盒 / 盖板 → 再看面板灯 → 最后才断电重启**。
- 教训：不要用「打一张测试页」来验证 USB。纸盒一合上，之前点过的作业会一起吐出来。

### v0.7.0 —— 本机文件打印 + USB 状态位

- App 内加「本机文件」面板：SAF 多选 → 流式复制到私有目录 → 字节嗅探 → 入队。
  `mime` 必须传 `*/*`（PCL / PS 没有统一 MIME），`EXTRA_INITIAL_URI` 指向 Download。
- **USB 状态位只有 bit3（PaperEmpty）可信**。缺纸真机返回 `0x18`、就绪返回 `0x20`，
  按 P1284 标准逐位翻译会得出「缺纸+故障+离线」这种荒谬结论。现在只报 bit3 和原始
  十六进制值。
- **缺纸时一个字节都不写**：以前写完 512KB 后端点 HALT，真实原因被「USB 写入失败」
  掩盖。现在 `JobStore` 提交前先查状态，缺纸直接 ABORTED（`resources-are-not-ready`）。

### v0.6.0 —— 通用直通

用户要求支持联想贴牌之外的机型。关键结论：**brlaser 的能力边界是「机芯」不是「品牌」**，
同一机芯的贴牌机（联想 LJ2600D / Brother HL-2240D 等）编码参数完全一致；真正无法
覆盖的是非 Brother 机芯。于是加了一条「通用直通」模式：不解码、不抖动，把客户端
送来的 PCL 原样转发，由打印机自己解释。

## 三、排查手册（同类现象先看这里）

### 「Android 搜不到这台打印机」

按这个顺序，别跳步：

1. `dumpsys print` 搜 `cached_printers` 里有没有目标的 `local_id`。
   **没有就是 BIPS 没提交，与 mDNS 无关**，直接去第 2 步，别浪费时间抓包。
2. `logcat --pid=$(pidof com.android.bips)` 搜三个词：
   - `canPrintPDF`（0 就是自述里没有 PDF，客户端会丢弃）
   - `number of values`（多值属性是否被解析全了）
   - `duplex:`
   这三个是 native 解析器的结论，**比任何自家检查器可信**。
3. 才轮到 mDNS：`dns-sd -B _ipp._tcp local.` 和 `dns-sd -L Cprinter _ipp._tcp local.`。
   注意 PC 上 5353 被多个进程抢占，自己写 socket 绑 5353 能 bind 但收不到包，
   会得出「0 条记录」的假结论。只能用 `C:\Windows\System32\dns-sd.exe`。
4. Windows 10 的「添加设备」不列 mDNS/IPP 打印机（只认 WSD 3702 + 蓝牙），
   **不要拿它当 mDNS 的验收标准**。

### 「改了 IPP 之后客户端行为变了」

先跑 `python tools/ipptest/ippcheck.py <ip>`。它现在会拦「连续两次写全名」。
再用 `python tools/ipptest/filtersim.py <ip>` 走一遍**过滤分支**——以前只测不过滤
分支，两条分支的代码不同，全量通过不代表过滤通过。

### 「两台手机同时开着无线调试」

`adb devices` 会同时列出两台，顺序不保证。脚本必须按 `dumpsys usb` 的
`host_connected=true` 选设备（插着打印机那台），否则会在错误的机器上排查，
看到的型号、版本、界面全是别人的实情。任何一次 adb 操作前先确认
`ro.product.model` + IP，并在同一条命令里输出。

## 四、留下的方法论

1. **自检工具的判据必须来自真实客户端**。`ippcheck.py` 和服务端一起错，绿了三个月。
2. **「没有报错」不等于「没有问题」**。BIPS 丢弃打印机的全程没有一条 ERROR。
3. **先做反证再下结论**。v0.7.4 的「服务没跑」能解释现象，但没做「服务跑着也没有」
   这个反证，所以它被当成了根因，多花了一天。
4. **别用真实出纸来验证协议**。纸盒一合上，积压的作业会一起吐出来。
5. **文档里的注释也可能是错的**，而且是错得最有说服力的那种（`IppServer.kt` 那条
   「1setOf 每个值都要带完整名字」）。写注释时要能指出 RFC 的具体条款号，否则
   它只是个人理解。
