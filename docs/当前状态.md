## 1. 一句话

把联想 LJ2600D（Brother HL-2240D 机芯）通过 Android 手机的 USB OTG 变成一台
**真正的局域网 IPP 打印机**，同时手机自己也能直接打印。全程非 Root、无 CUPS、
无 chroot、无 MuPDF/Poppler/Ghostscript。

## 2. 能力矩阵

| 谁在打 | 走什么入口 | 文档格式 | 状态 |
|---|---|---|---|
| iPhone / iPad / Mac | AirPrint（mDNS `_universal` 子类型 → IPP） | `image/urf` | ✅ 真机出纸 |
| 局域网 IPP 客户端（ipptool 等） | IPP 端口 8631 | PDF / URF / PWG / PCL | ✅ 全通 |
| Windows（厂商驱动，无 IPP 类驱动） | IPP → 字节嗅探 → **PCL 原样直通** | PCL | ✅ 出纸 |
| Windows（IPP Class Driver） | IPP → PWG Raster 解码 | `image/pwg-raster` | ✅ CRC 逐字节对账 |
| 手机自己（WPS / 相册 / Chrome） | Android 打印框架插件 | PDF | ✅ 出纸 |
| 任意一台 Android（含另一台手机） | 系统打印服务 BIPS → mDNS → IPP | PDF / PWG Raster | ✅ 列表可见可选（v0.7.5 修） |

## 3. 架构

```
入口（三条，互不干扰）
  ├─ iPhone / iPad / Mac ── AirPrint，mDNS _universal 子类型，送 image/urf
  ├─ Windows ── IPP 端口 8631；厂商驱动送 PCL，IPP 类驱动送 PWG Raster
  └─ 手机自己 ── Android 打印框架插件，送 PDF
        │
        ▼
  IPP / HTTP 服务器（8631，手写，无第三方依赖）
  Ipp.kt 编解码 · IppServer.kt 属性与作业 · JobStore.kt 串行队列
        │
        ▼
  DocumentSniffer —— 看字节决定走哪条路，不信客户端声明的 document-format
        ├─ PDF  → PdfRenderer（超 64MB 自动切条带，每带 256 行）
        ├─ URF  → URF 解码器（AirPrint；游程语义与标准 PackBits 反向）
        ├─ PWG  → PWG 解码器（无厂商驱动的 Windows）
        └─ PCL  → 不解码，原样直通 ────────────────────┐
        │                                            │
        ▼                                            │
  RasterPage（宽/高/dpi/灰度 + duplexHint）            │
        │                                            │
        ▼                                            │
  brcore.cpp 抖动 + brlaser 编码（统一 600dpi）        │
        │                                            │
        └──────────────┬─────────────────────────────┘
                       ▼
  USB Bulk Transfer（单次 ≤16384 字节，-1 退避重试后必须报错）
                       ▼
              联想 LJ2600D / HL-2240D
```

## 5. 最近打通的事

2026-11-16 打通的是四条主链路（AirPrint 出纸 / URF 600dpi / 双面 / 多份），逐条证据
见 `docs/Stage*-验收记录.md`。2026-11-19 之后的进展按版本记在 `docs/开发日志.md`。

其中 v0.7.5 修掉的是拖得最久的一条：**Android 系统打印列表里一直看不到这台机器，
根因是 IPP 的 `1setOf` 多值属性写成了「重复全名」**，BIPS 的 `canPrintPDF` 恒为 0，
于是它静默丢弃整台打印机。修后 `canPrintPDF: 1`、`duplex: 1`、`media-supported`
读到 3 个值，两台手机的系统列表里都能看到 `Cprinter`。

## 6. 那些「看起来奇怪但必须这样」的决策

这一节是给未来的自己和接手的人看的。每条都对应一次真机故障。

### 6.1 双面的三层修复

1. **`ESC&l2S` → `ESC&l1S`**。上游 brlaser 发的是短边双面，而 HL-2240D 的双面单元
   只有长边翻页；短边命令被静默忽略，当成单面打。修在 `brcore.cpp` 的 `finish()`
   里替换字节（`job.cc` 是上游文件，不动），只换第一处。
2. **网络作业不继承界面设置**。`JobStore.resolveDuplex()` 是 `fromClient ?: false`。
   界面底部的「单/双面」只给「系统打印（手机）」和「测试页」用。
3. **iOS 的双面意图只在 URF 页头**，IPP 的 `sides` 属性根本不发。由
   `RasterPage.duplexHint` 承载，首页到达时覆盖界面值。

**遗留的语义差异（已知，暂不处理）**：URF 页头给的是 `3`（短边），我们发的是长边。
对 A4 竖版文档这是标准做法 —— 像书一样左右翻，背面正立。但如果以后打**横向文档**
时发现背面方向不对，根源就在这里：那时要按 URF 的 `2`/`3` 分别发 `ESC&l1S`/`ESC&l2S`，
而不是一律长边。

### 6.2 分辨率强制 600

`PRINTER_DPI = 600`，不采信文档页头。这台机芯的规格写着「2400×600」，但 2400 是
纵向抖动插值的观感，**可选的光栅采样率只有 600 一档**。按 300 编码会发
`@PJL SET RESOLUTION = 300`，机芯不认、整页丢弃、不报错 —— 一张纯白纸。

宁可把 300dpi 文档重采样到 600 网格（清晰度不会变好，但打得出来），
也不能把页数正确的数据整页丢掉。

### 6.3 份数交给打印机

`ESC&l#X` 让打印机自己重复整个作业。3 份的 PCL 仍是 288105 字节，与 1 份完全相同。
若在应用层把每页编码 N 遍，99 份就是 28MB，而 USB 只有约 1.5MB/s。

### 6.4 TXT 与 IPP 必须同源

mDNS TXT 里任何一个能力位，IPP 侧都要有**对应且等价**的声明，否则客户端判自述矛盾：
面板给了选择器，提交却通不过。已经踩过两次（`Duplex`/`sides-supported`、
`Copies`/`copies-supported`）。

现在的一致关系：

```
TXT  Duplex=T  DM1,DM3  ⟷  IPP sides-supported=(one-sided, two-sided-long-edge)
TXT  Copies=T           ⟷  IPP copies-supported=1..99
TXT  URF=...,RS600,...  ⟷  IPP urf-supported=(1setOf keyword) + printer-resolution-supported=600
TXT  UUID=urn:uuid:X    ⟷  IPP printer-uuid=urn:uuid:X（逐字节相同）
```

### 6.5 报文审查必须用「陌生解析器」

项目里反复出现同一类 bug：**服务器和自测工具共用错误理解，两边自洽、测试全绿，
而真实客户端一句话不说就放弃。** 已踩过：操作码整体错位、`urf-supported` 类型错、
`printer-input-tray` 当成 collection、同一属性发两遍、默认值不在支持集里。

最贵的一次是反向的：检查器里写着「`1setOf` 的第 2..n 个值也必须带完整属性名」，
服务端照着这条实现，于是 `document-format-supported` 只剩第一个 `image/urf`，
Android 的 `canPrintPDF` 恒为 0，打印机在系统列表里根本不存在 —— 全绿了三个月。
真正的规则是**只有第一个值带名字，后续值 name-length 必须为 0**（RFC 8010 §3.1.5）。

所以 `tools/ipptest/ippcheck.py` 只做一件事：把响应当成**陌生人写的报文**审，
不借任何自家常量，逐条查结构性自洽。判据必须来自真实客户端（CUPS / PrintKit）
的行为，不能来自实现者的理解。当前 0 问题。

### 6.6 端口只能是 8631

非 Root 应用无法 `bind()` < 1024。服务器接受任意 POST 路径，所以 Windows 侧
只改端口号、保留旧路径也能工作。

### 6.7 对外地址只用 `net/NetInfo`

开 VPN 时 `ConnectivityManager` 里 VPN 网络也带 WIFI 传输类型，自己遍历网卡会选中
`tun0` + `100.64/10`，客户端连不上。必须跳过 `TRANSPORT_VPN` 和缺 `NOT_VPN` 能力的网络。

### 6.8 logo 是矢量，且打印时不能走 `VectorDrawable.draw()`

位图 logo 放大就糊（启动页铺满、纸上按分辨率缩放），所以源头是矢量：
`tools/mklogo.py` 从 `tools/logo/logo-src.jpg` 描线，生成 `drawable/ic_logo.xml`
与 `values/logo_path.xml` 两份**同源**资源，改图只改脚本。

打印那条路必须用 `PathParser` 把 pathData 还原成 `Path` 再 `drawPath`。
直接 `draw()` 一个 VectorDrawable 时，它带 tint 会走自己的 bitmap 缓存，
**按 bounds 栅格化**——生成出来的 PDF 里那 30pt 的 logo 是一张 30x30 像素的
`/Subtype /Image`（v0.7.7 实测）。屏幕上完全看不出来，只有拆 PDF 才暴露。

### 6.9 对外名称只有一处来源，改名必须注销重注册

打印机名同时是 mDNS 实例名（客户端列表那一行）和 IPP 的 `printer-name`，唯一来源是
`AppSettings.effectivePrinterName()`。两处不同源的表现是「列表里叫客厅打印机、
点进去的打印面板写 Cprinter」，用户会以为加错机器。

改配置字符串**不会**让已经在跑的服务改名 —— 名字是注册那一刻写进 PTR/SRV 的。
`PrintService.liveInstance` 记着实际发出去的名字，与配置不一致时先停广播、等 400ms
（`NsdManager.unregisterService` 是异步回调，紧接着注册会撞 `FAILURE_ALREADY_ACTIVE`）
再重新注册。

名字是 DNS 标签：上限 **63 字节**（一个汉字 3 字节），不能含点（会被当分隔符，
系统转义成 `\.` 而自写 responder 不转义，两边对不上）。超限时 `NsdManager` 只回
`FAILURE_INTERNAL_ERROR`，不说原因，现象是「改名后一个客户端都搜不到」。

## 7. 已知限制

- 只构建 `arm64-v8a`。
- **没有 AAAA 记录**：纯 IPv6 局域网里 iOS 找不到本机。也没做名字冲突探测。
- 作业状态不持久化：进程重启后 job-id 从 1 重来。
- PCL 直通路径下，App 里的「画质/单双面」不生效 —— 渲染方是 Windows 驱动。
- 加密 / 复杂 PDF 不支持（`PdfRenderer` 的限制）。
- 面板 `GET_PORT_STATUS` 返回 `0x18`，位定义未定标：USB 规范与 IEEE 1284 对
  这一位的解释相反，目前只显示不据此决策。
- `finishings-col-database` / `printer-charge-info-uri` **故意不声明**。
  `printer-mandatory-job-attributes` 按 RFC 写法给 `1setOf keyword = none`（空集的
  标准写法）——v0.7.6 之前这里漏声明，iOS PrintKit 判「状态不明」，连作业都不提交，
  现象是 AirPrint「点了没反应」。
- App 图标没跟新 logo 同步（用户要求保持原样），所以桌面图标和测试页/启动页的图不是同一张。

## 8. 环境与操作

```bash
./build.sh                              # 构建（自动 subst W:，绕开中文路径）
./build.sh :app:externalNativeBuildDebug # 改 C++ 后必须显式跑，否则 .so 不重编
./tools/adb.sh <args>                   # 联调一律走这个（自动 mDNS 发现 + 重连）
python tools/ipptest/ippcheck.py <IP>   # 协议一致性审查，退出码 0 = 全通过
python tools/ipptest/mdnsquery.py --subtype   # 查 AirPrint 子类型广播
```

零耗纸验证：`run-as <pkg> touch cache/dryrun` → 提交作业 → 读 `cache/jobs/last-encoded.pcl`。
**用完必须 `rm cache/dryrun`**，否则后续真实打印全部静默跳过 USB。

## 9. 建议的下一步

按价值排序：

1. **作业状态持久化**。现在进程一重启，客户端已经提交的 job-id 就查不到了，
   iOS 的打印中心会卡在「正在打印」。
2. **AAAA 记录 + 名字冲突探测**。纯 IPv6 网络和「两台同型号手机」这两个场景
   现在都会失败，且都不报错。
3. **面板状态定标**。`0x18` 究竟是缺纸还是别的，需要用已知状态（抽出纸盒、
   打开前盖、合上盖板）逐项对照实测。这一条是下一条的前提。
4. **`printer-state-reasons` 与真实缺纸联动**。现在这个属性**硬编码为 `none`**，
   而 USB 端口状态已经能读到 `0x18`（其中包含 PaperEmpty 位）。
   不敢映射的原因正是上一条：位定义没定标，误报「缺纸」会让客户端直接拒绝
   提交作业 —— 比不报更糟。所以顺序必须是**先定标、再联动**。

   现状的后果：缺纸时 iOS 仍显示 Ready，用户看到「正在打印」却不出纸，
   只能从 App 日志里看到 `PaperEmpty`。
